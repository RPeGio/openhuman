# 技术卡 6：为什么需要三层架构？

## 一句话

把 UI、桌面壳、业务逻辑分成三层，不是因为"应该这样"，而是因为**每一层有不同的技术需求，混在一起会互相拖累**。

## 反例：如果只有一层

假设你用 Electron + Node.js 把全部代码写在一起：

```
index.js
├── 渲染 UI（React 组件）
├── 管理窗口
├── 调用 LLM
├── 操作文件系统
├── 管理 Agent 推理循环
└── 同步 Gmail 数据
```

问题：

1. **一个崩溃全死**：LLM 调用超时 → 整个窗口卡住 → 用户以为应用死了
2. **技术栈互斥**：渲染 UI 适合 JS/TS（生态好），但 CPU 密集计算（嵌入向量、记忆压缩）不适合 JS（单线程）
3. **测试困难**：改一个 UI 文案要重新测试所有 Agent 逻辑
4. **部署不灵活**：如果你想把核心部署到服务器上（headless 模式），你不能——它和 UI 绑死了

## 三层架构解决了什么

```
                   如果崩溃了...          技术选择          部署灵活性
┌──────────┐      ┌──────────┐      ┌──────────┐      ┌──────────┐
│  React   │  →   │ UI 崩了   │  →   │ TS/JS    │  →   │ 只能是   │
│  前端    │      │ 核心还在  │      │ 生态最好 │      │ 桌面 UI  │
├──────────┤      ├──────────┤      ├──────────┤      ├──────────┤
│  Tauri   │  →   │ 壳崩了    │  →   │ Rust     │  →   │ 绑定桌面 │
│  桌面壳  │      │ 前端还在  │      │ 原生速度 │      │ 平台     │
├──────────┤      ├──────────┤      ├──────────┤      ├──────────┤
│  Rust    │  →   │ 核心崩了  │  →   │ Rust     │  →   │ 可以独立 │
│  核心    │      │ 会重启    │      │ +Tokio   │      │ 部署到云 │
└──────────┘      └──────────┘      └──────────┘      └──────────┘
```

## 每层的"为什么"

| 层 | 为什么选这个技术 | 如果不分层会怎样 |
| --- | --- | --- |
| React 前端 | TS/JS 生态有最好的 UI 框架、状态管理、组件库 | 用 Rust 写 UI 极慢（开发效率低） |
| Tauri 壳 | 原生窗口管理 + CEF webview 的能力 | 和核心混在一起会让 WebView 生命周期污染 Agent 逻辑 |
| Rust 核心 | 高并发、无 GC、内存安全、编译为原生二进制 | 用 Node.js 处理嵌入计算会阻塞整个 event loop |

## 真实类比：餐厅

```
React 前端 = 服务员（和顾客沟通，展示菜单）
Tauri 壳  = 餐厅的建筑（提供空间，管理餐桌）
Rust 核心 = 厨房（真正"做菜"的地方）
```

你不能让服务员同时炒菜（会烧糊），也不能让厨房直接面对顾客（沟通效率低）。分开各司其职，整体效率最高。
